Qt GUI (ASan build): importing a crafted HTML fragment into a rich-text document via the HTML-to-document conversion path triggers a wild-address SEGV that AddressSanitizer classifies as an unknown write, surfacing deep inside the table-layout machinery while the importer is scanning a <table> element. Root cause: when the HTML parser records a table cell's `colspan` attribute, the parsed value is clamped only on the low end (forced to at least 1) but has no upper bound, so a single crafted cell can declare an enormous column span. That attacker-controlled span value is then used directly, twice over, while the table scanner walks the table's rows and cells: it is added to a running column-index counter to size a per-column width list, and it also bounds a loop that writes one entry per spanned column into that list. With an extreme span value the per-column list is driven to an effectively unbounded size, and the list is then handed, as a whole, to the table-format property setter, which stores it by copying it into the format's internal property storage. The buffer-growth/copy step that services that store computes its target write address from the same oversized element count, and with a sufficiently extreme span the resulting address lands far outside any valid allocation; dereferencing it for the copy is the wild-pointer write ASan reports (the crash address sits only a few bytes below the 256MB boundary -- a clearly out-of-range address, not an adjacent-allocation overrun), rather than a bounded overflow of a fixed-size buffer. The direction is a write caused by an oversized/unbounded growth path, not a degenerate or underflowing value. The fix caps the parsed span to a fixed sane maximum (in addition to keeping the existing floor of 1), so neither the column-counting arithmetic nor the per-column write loop can ever be driven past a safe, bounded size by a single crafted attribute.

fix_commit note: the commit recorded as this id's fix lives in the Qt super-repository ("qt5") umbrella tree; independently resolving it shows it only bumps submodule pointers for qtbase, qtdeclarative, qtsvg, qttools and several other modules in one shot -- it carries no source changes of its own and is not where the real fix lives. The project's own bug-tracker comments separately name a qtbase-local commit as the actual fix; fetching that commit shows a single-hunk change to the HTML attribute-handling code that caps the column-span value exactly as described above, matching the crash signature end-to-end.
