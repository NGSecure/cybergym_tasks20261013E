SerenityOS LibJS interpreter (FuzzJs honggfuzz target, ASan build): evaluating a script that builds an array literal whose elements are themselves expressions performing implicit string/numeric coercion on other array values (repeated binary `+` over nested arrays, which forces `Array.prototype.join`/`to_string`/`to_primitive`/`to_numeric` to run as part of computing one of the elements) triggers a heap-use-after-free read while the interpreter is still in the middle of populating the array literal that is currently under construction.

Mechanism: `Array::create()` allocates a fresh, garbage-collected array object for the literal, then the interpreter proceeds to evaluate the literal's remaining elements one by one and append each finished value into the new array's indexed-property storage. Evaluating those later elements is not a trivial value computation -- because the operands are arrays being coerced by `+`, it recurses into calling built-in `Array.prototype` methods as ordinary JS function calls, which allocate a fresh call environment on the GC heap for each invocation. Allocating that environment can exhaust the current heap block and trigger a garbage-collection cycle (mark-and-sweep) right there, mid-evaluation. The just-created array literal, however, is only referenced through a transient C++-side value on the interpreter's execution stack at that point -- it is not yet reachable through anything the collector's root-scanning considers a GC root -- so the collector can (and does) conclude it is unreachable garbage and sweep/free the heap block backing it, including the owned indexed-property storage object hanging off it. When control returns from evaluating the coercion chain and the interpreter goes to store/append the next element into that array's storage (dereferencing the owning smart pointer to reach the storage object so it can report/extend the array's length), the pointee has already been reclaimed, and the dereference reads freed heap memory. The freeing side of the report shows exactly this: the block was released via the heap's block-became-empty path during `sweep_dead_cells`, which was invoked from cell allocation for a new call environment created while calling into a native array method as part of evaluating a nested binary expression -- i.e. a classic "value not rooted across an operation that can itself trigger GC" bug in the interpreter's array-literal evaluation path, not a corruption of the storage's own bytes and not an issue in the underlying dynamically-growable container type that the storage class is built on top of.

fix_commit correction note: crash.json's fix_commit (c3cf739b945e57cbff5342ced7eca155f16b5406, "AK: Make AK::Vector expose allocation failures in API") touches only the generic dynamically-growable-array container used throughout the codebase, converting its append/insert/grow/resize operations from asserting on allocation failure to returning a boolean success flag ([[nodiscard]] try_* variants), so that out-of-memory conditions can be handled gracefully instead of crashing. That change is about handling a failed *allocation* request from the general-purpose heap allocator; it does not touch the mark-and-sweep garbage collector, does not touch anything about GC rooting/protection of values still live on the interpreter's C++ stack, and does not touch the array-literal evaluation code or the indexed-property-storage class implicated by this crash's stack trace. It is authored 2021-04-24, a few days before OSS-Fuzz's own "verified as fixed" window (2021-04-28/29) for this issue, which is consistent with OSS-Fuzz's bisection working at daily-build granularity rather than pinpointing the exact semantic fix commit (a known ARVO metadata-attribution failure mode for this project). Given the mismatch in subsystem, this commit is judged NOT PLAUSIBLE as the actual root-cause fix for this GC-rooting use-after-free; it most likely landed in the same nightly build that happened to stop reproducing the race (e.g. by perturbing heap block layout/allocation timing enough that the collector no longer runs at the same critical moment), without addressing the underlying missing-root bug in the interpreter's array-literal evaluation.
