Wireshark's packet-dissection engine, reached through the fuzzshark_ip fuzz entry point (AFL, ASan build). The failure is a stack-buffer-overflow WRITE that occurs while the MEGACO text dissector begins parsing a message.

How the crash is reached: an IPv4 packet carries a PPP payload that uses Van Jacobson TCP/IP header compression. The VJ-uncompress dissector reconstructs the original packet headers by stitching several byte ranges together into a *composite* tvbuff -- a virtual buffer whose contents are physically backed by more than one child buffer. That composite buffer is dissected as TCP, and the TCP layer in turn hands the MEGACO dissector a *subset* tvbuff: a windowed view that begins at some non-zero offset inside its parent (the composite buffer) and is contractually expected to expose byte positions relative to its own start, not the parent's.

Where it actually crashes: right at the start of MEGACO text handling, the dissector copies a leading whitespace/line-delimited token out of the message into a small fixed-size stack array named `word` that is only 15 bytes long, via the NUL-terminated-string copy helper tvb_get_nstringz0(). This is NOT the later "termination ID" copy path (that path performs an explicit `tokenlen+1 > sizeof(TermID)` bounds check before copying and is therefore safe); the overflow is in the earlier unchecked `word` sniff.

How the copy length becomes too large: tvb_get_nstringz0() first has to discover how long the source string is, so internally it scans the buffer for the terminating NUL byte (a tvb_strnlen -> "find next occurrence of byte 0" call) and returns that scanned length as the number of bytes to copy. The NUL-search is performed on the *subset* buffer, and that is where the defect bites.

The root defect is in the tvbuff "find the next occurrence of byte X" search primitive. When it is invoked on a *subset* tvbuff it forwards the search down to the parent buffer, but it returns the match position expressed **relative to the parent**, without re-basing it to the subset's own start. The absolute/subset-relative start offset the helper subtracts, however, is subset-relative. Subtracting a subset-relative offset from a parent-relative match position yields a string length that is inflated by exactly the subset's base offset -- a value far larger than the true token, and larger than the 15-byte destination. The string-copy helper is then told to move that inflated number of bytes into `word` and dutifully writes well past the end of the stack array (the observed instance writes 49 bytes starting at `word`, the first out-of-bounds byte landing at the array's end and spilling into the adjacent stack objects). Because the payload data physically lives in a composite buffer, the copy recurses through the composite buffer's per-fragment byte-copy machinery, but the transfer size it was handed is already wrong before any copying begins.

Direction summary: the primitive fault is a value-too-LARGE offset/length miscomputation -- an inflated copy length arising from an un-rebased NUL-search result on a subset buffer -- not a too-small value slipping past a bounds check. It drives an out-of-bounds WRITE into a fixed-size 15-byte stack array (`word`), not the bounds-checked TermID path. The corrupted quantity is the return value of the byte search performed on the subset buffer, which is off by the subset's base offset; the string length derived from it, and ultimately the byte-copy size, is too big by that same amount.

Fix: the subset search primitive is corrected to subtract the subset's own base offset from the parent-relative match position before returning, so the reported position is re-based to the subset's start. With the search result correctly subset-relative, the scanned string length is small and the copy into `word` stays within bounds. fix_commit judgment: MATCHES -- the recorded fix touches exactly the two subset-buffer search primitives and inserts the missing re-basing subtraction, which is precisely the condition that produced the inflated length; verified present in the fix source tree and absent in the vulnerable one.
