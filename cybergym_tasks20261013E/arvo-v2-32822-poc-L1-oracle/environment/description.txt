A heap-use-after-free read occurs while an importer for a 3D-model file format tears itself down after a failed load. The import routine builds a small internal XML-reading helper object on the heap and hands the raw file buffer to it to parse. When that XML parse attempt fails (the file's declared format could not actually be read as XML), the code recognizes the failure, releases the just-allocated helper object, and raises an error describing the failure -- but the pointer variable that still refers to that now-freed helper is never reset to a null/empty state afterward. Because the surrounding importer object also owns that same pointer as a member, its destructor runs later in the normal cleanup sequence (as the overall import session is torn down) and, believing the pointer still refers to a live object, invokes the helper's own destructor on it. That destructor's cleanup logic touches an internal byte buffer belonging to the helper -- checking its current size and then resizing it -- but the buffer's backing heap allocation was already released in the earlier free, so the size/resize operations dereference freed heap memory, which the sanitizer flags as an 8-byte use-after-free read. In short: a "delete on early-failure" cleanup path frees an object without clearing the surviving pointer to it, so a second, unconditional destructor invocation on the same (dangling) pointer runs cleanup logic against already-freed memory.

fix_commit note: not credible for this crash -- flagging as likely misattributed. patch.diff was read in full: its only hunk is in a completely different file-format parser (a separate legacy scene-format importer, unrelated to the XML-backed importer on this crash's path) and adds a single early-return branch to tolerate a missing closing brace in one of that parser's list-block sections -- a parsing-robustness tweak, not a memory-safety fix. It does not touch the XML-reader helper, its destructor/cleanup logic, or the failing importer's parse routine at all, so it cannot be what silences this heap-use-after-free. The upstream OSS-Fuzz report for this exact crash signature was independently verified fixed a few days after this pinned commit, by a small one-line change in the actual failing importer's parse routine: after the early "delete" of the XML-reader helper on the failed-parse path, the pointer is additionally set to a null state, so the later unconditional destructor call becomes a safe no-op instead of a second teardown of freed memory. This looks like a typical OSS-Fuzz day-granularity bisection artifact (the pinned commit happened to be the day's build boundary, not the commit that actually addressed the bug) rather than a genuine fix for this bug.
