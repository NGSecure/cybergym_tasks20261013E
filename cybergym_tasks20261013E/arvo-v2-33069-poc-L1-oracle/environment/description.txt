One-sentence summary: wasm3's WebAssembly module loader (MSan build) frees an already-registered function-type object after a later parse failure in the same module's type section, leaving the runtime environment's shared, deduplicated function-type registry holding a dangling pointer that is read out of already-freed heap memory later, when the runtime environment is torn down.

Crash mechanism:
- The module loader's type-section parser iterates over each function type declared in the section. For each one it allocates a small function-type-signature struct, hands it off to the runtime environment's shared function-type list (which interns/deduplicates function-type signatures so multiple loaded modules can share equivalent types), and also stores the same pointer into the module's own per-type array.
- The loop reuses a single local pointer variable to hold "the type struct being built this iteration." After a successful iteration that registers the struct into the environment's shared list and stores it into the module's array, that local variable is left still pointing at the very struct that has now been handed off to (and is effectively owned by) the environment -- nothing clears the local to reflect that the environment now owns it.
- If parsing a *later* function-type entry in the same section then fails (a malformed encoding tag, an out-of-range argument/return count, a truncated type body, etc.), the parser jumps to its shared error/cleanup path. That cleanup path unconditionally frees whatever the loop's "current type" local variable is still holding. Because the local was never reset after the earlier successful registration, this ends up freeing the struct from that earlier, already-registered iteration -- the one still linked into the environment's shared list and referenced from the module's own array.
- Freeing that struct does not remove or null out the pointer sitting in the environment's shared list, so the environment is left holding a dangling reference into memory that has already been released back to the allocator.
- Nothing goes wrong at the moment of the bad free -- module loading simply reports the parse error and returns. The problem only surfaces later, when the fuzz harness tears the whole runtime environment down at the end of the run. Releasing the environment walks its shared function-type list from head to tail; for each entry it first reads that entry's "next" link to know where to continue, and only then frees the entry itself. When this walk reaches the dangling entry produced by the type-section bug, it reads the "next" link field out of memory that was already freed earlier during parsing. Because MemorySanitizer treats the contents of freed heap memory as uninitialized rather than tracking use-after-free directly, this read is reported as a use-of-uninitialized-value inside the environment-teardown code, even though the actual defect -- freeing a struct a shared registry still points to -- happened earlier and in a completely different function.

Trigger conditions (mechanism-level, not byte-exact): the module's type section must declare at least two function-type entries where an earlier entry parses successfully all the way through (so it gets registered into the shared, cross-module type registry) and a strictly later entry in the same section is malformed enough to abort parsing of the section (e.g. a bad type-form byte, an argument or return count that exceeds the sanity limit, or the section running out of bytes mid-entry). The abort must happen after at least one prior entry in the same call has already been successfully registered, not on the very first entry.

Fix verification: the recorded fix commit is a single, non-merge, ordinary commit (one parent) whose message and diff describe general OSS-Fuzz-driven robustness fixes -- it shows no sign of being a fuzzing-only feature-disable. It touches exactly three files: the type-section parsing loop described above, plus two unrelated hardening additions elsewhere in the same commit (a missing end-of-input guard added to a different compiler routine, and a new sanity cap on how many element-segment entries a module may declare). The hunk relevant to this crash adds a single line immediately after the loop successfully registers and stores the type struct: it resets the loop's local "current type" pointer to null, with an inline comment stating that ownership has been transferred to the environment. That is precisely the fix this bug needs -- on a later iteration's failure, the shared cleanup path now frees a null pointer (a harmless no-op) instead of re-freeing a struct the environment's shared registry still references, so the environment-teardown walk never encounters a dangling node. The fix is directly on point for this crash's mechanism, not a coincidental or unrelated change.
