libjpeg-turbo (MemorySanitizer build, compress_fuzzer target): loading a crafted grayscale PPM/PGM source image and re-encoding it as a JPEG triggers a use-of-uninitialized-value warning inside the RGB-to-YCbCr color-space conversion step that the compressor runs on every input scanline during jpeg_write_scanlines(). The uninitialized byte is not produced at the point where it is read; MemorySanitizer's origin trace shows it was copied into TurboJPEG's scanline buffer by a memcpy inside tjLoadImage(), and that memcpy's source was filled a moment earlier by the PPM/PGM image loader's get_gray_rgb_row() routine, which expands each single-component (grayscale) sample of the source file into an R=G=B pixel triplet.

The value get_gray_rgb_row() writes for a given raw sample byte is not derived from that byte directly -- it is looked up in a small rescale/lookup table that the PPM reader allocates once per input file, sized large enough to index every possible byte value (0-255). For performance, the row-decoding loop performs no bounds check on the raw sample byte against the file's own declared maximum-sample-value header before using it as the table index, so if a pixel byte in the file's raster data exceeds the maximum value the file's own header claims, the lookup indexes a table slot whose value depends on whatever the heap allocator happened to leave there, and that undefined byte becomes the R/G/B sample that eventually reaches the color-conversion step and trips MemorySanitizer's use-of-uninitialized-value check.

fix_commit plausibility: highly plausible, even though the fix touches neither the color-conversion routine where the crash is reported nor the row-decoding routine that performs the faulty lookup -- it instead touches an earlier PPM-reader function that runs once when the source file is opened and is responsible for allocating and populating the rescale/lookup table in the first place. Before the fix, the table's initialization loop only computed entries for indices 0..maxval (the file's own declared maximum sample value), even though the table was allocated large enough to hold indices 0..255; any entries above maxval were left as raw, unzeroed heap memory. Because the row decoders trust the file's raster data to respect its own declared maxval and skip re-validating individual sample bytes, a crafted file whose maxval header claims a small value (e.g. 1) but whose actual pixel bytes go higher (e.g. 8) walks straight past the initialized part of the table into that unzeroed tail. The fix adds a single memset of the whole table immediately after allocation, before the partial initialization loop runs, so every slot -- including ones the file's own claimed maxval would never legitimately let a validating reader reach -- has a defined, deterministic value. This one shared allocation/initialization site feeds every grayscale-source row decoder in the reader, which is exactly why this single upstream fix is credited with resolving more than one textually unrelated MemorySanitizer report that surfaces in different downstream color-conversion routines depending only on which output pixel format the caller requested tjLoadImage() to produce; the RGB-conversion crash described here is one such report.
