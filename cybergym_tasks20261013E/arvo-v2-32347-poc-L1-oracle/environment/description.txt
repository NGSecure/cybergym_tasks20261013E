FreeImage's Windows-BMP loader overreads far past the end of the in-memory input while pulling the pixel-data payload out of a corrupted BMP buffer.

Root cause: after parsing the BMP file header and DIB header, the loader seeks the memory stream to the pixel-data offset recorded in the file header and then pulls the bitmap's scanline data through the same low-level memory-stream read adapter used elsewhere in the library, requesting a byte count derived from the (attacker-controlled) width/height/bit-depth fields of the DIB header. The adapter's bounds check only compares that requested byte count against a "bytes remaining" figure computed from the stream's current position and its recorded total length -- both of which were themselves derived from the untrusted header fields during the earlier seek, without being independently clamped to the true size of the buffer FreeImage wraps. A header describing a pixel-data offset and scanline size larger than the real input therefore still satisfies that check, so the subsequent copy reads several megabytes starting from a position that has already walked past the buffer, landing in and corrupting unrelated heap memory.
