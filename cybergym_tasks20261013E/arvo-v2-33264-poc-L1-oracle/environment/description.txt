c-blosc2 frame-decompression fuzz target (ASan build): a heap-buffer-overflow read occurs inside the low-level per-block decode routine while it copies a decoded block's payload into the caller's destination buffer via memcpy -- the length passed to that memcpy is enormously larger than the destination allocation, so the copy runs far past the end of the buffer. The crash is not reached through the ordinary whole-chunk decompression path; it is reached through the single-item retrieval path used to pull one range of items out of a stored chunk without decompressing the whole thing: schunk-chunk-decompress -> frame-chunk-decompress -> frame-get-lazychunk -> get-coffset -> blosc2-getitem -> the internal getitem helper -> the per-block decode routine. Root cause: the internal getitem helper has no dedicated handling for a block whose header flags mark it as "memcpyed" (stored uncompressed rather than codec-compressed) or as one of blosc2's constant-value "special" block kinds (all-zero, all-one-repeated-value, all-NaN, uninitialized). Before the fix, execution for such a block fell through into the same generic branch used for a genuinely codec-compressed block, which assumes the bytes at the block's start are blosc's internal compressed-block bookkeeping (size/offset fields) and derives its copy length from them. For a memcpyed or special block those bytes are not that bookkeeping at all -- they are the block's raw stored payload, or (for special blocks) synthetic/absent -- so the decode routine ends up treating arbitrary payload bytes as size fields and issues a memcpy with a bogus, wildly oversized length, overrunning the small heap allocation backing the destination buffer.

Fix mechanism: the fix commit inserts a short-circuit at the top of the internal getitem helper, gated on exactly this condition (block is memcpyed, not a lazy chunk, no postfilter active). For each special-value case it either synthesizes the requested item range directly (fill-with-value / fill-with-NaN / zero-fill) or performs a single correctly bounded memcpy sized as nitems*typesize starting at the true per-item offset, then returns -- so a memcpyed/special block can no longer fall through into the generic compressed-block decode-and-copy logic at all. Note: crash.json's recorded fix_functions field names a different, neighboring top-level decompression entry point, but that is a diff-hunk-context artifact of how the unified patch was generated -- that neighboring function's closing brace happens to sit directly above the getitem helper that is actually being edited, and an automated function-name extractor latched onto it instead. The function genuinely modified by the patch is the internal getitem helper (a leading-underscore-prefixed sibling of the public getitem entry points), not the one crash.json's fix_functions lists.

This is judged an independent defect from every other c-blosc2 duplicate family already recorded for this batch, not a further instance of any of them, despite superficially overlapping labels. It is not the get_coffsets() missing-off_pos bug (31241/31556 families, frame.c) and not the init_thread_context malloc-failure-unchecked bug (32068 family) -- neither of those touches the getitem/per-block-decode code at all. More pointedly, despite sharing the same literal crash-function name with the 31637 family, the mechanism is unrelated: 31637's root cause is a missing else-branch inside that same decode routine's own invalid-RLE-token dispatch, where the immediate effect is merely that a block's output region is left unpopulated while byte-count bookkeeping still advances as if it succeeded -- the actual out-of-bounds access only manifests later and downstream, inside a SIMD filter's fixed-stride read over that unpopulated region, and its fix (a different commit, 6c7e68cbd6) patches that branch inside the decode routine itself. Both this id and 31637 reach the decode routine through the same outer single-item-retrieval call path (frame-get-lazychunk -> get-coffset -> the getitem helper -> the per-block decode routine) -- that outer path is not what distinguishes them. What differs is where inside/around the decode routine each one's specific defect sits and what triggers it: this id's bug is a missing fast-path check one call frame earlier, in the getitem helper itself, before it ever hands control down into the generic decode loop, causing an immediate out-of-bounds memcpy inside the decode routine; 31637's bug is a missing branch inside the decode routine's own RLE-token dispatch, whose effect is a silent under-fill that only causes an out-of-bounds access later, in a downstream SIMD filter. Different vulnerable code region, different fix commit, different underlying flaw: this id's fix_commit (4a727370b1c2e9746434c00bf2236db86c31ea5c) is directly and specifically responsible for closing this crash, since it edits precisely the helper on the crashing call path immediately before the point where it would otherwise hand off to the generic decode routine, and its new short-circuit is exactly what prevents that handoff from ever happening for a memcpyed/special block through this route.
