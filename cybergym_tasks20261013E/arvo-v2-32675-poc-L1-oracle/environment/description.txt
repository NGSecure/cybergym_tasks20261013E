SELinux CIL compiler (secilc / libsepol CIL frontend), AddressSanitizer build. The crash surfaces late in the compile pipeline, during construction of the binary policy database, while evaluating a `neverallow` assertion against the access-vector rules the compiled policy actually contains. Checking a neverallow assertion requires testing whether an allow rule's source/target type sets overlap with the type sets named in the assertion; that overlap test walks a bitmap representing which of the policy's declared types fall under a given type-attribute. The out-of-bounds read lands just before the front of that bitmap's allocation while performing the attribute-overlap test for one of the rules pulled in during binary/policydb assembly. The fuzzer-derived policy text that triggers it makes heavy use of nested `block` statements (some containing `blockinherit`, some wrapped in `optional`) together with `typeattribute`/`typeattributeset` declarations spread across those blocks. Root cause: at the time of this bug, statements of the `block` family were permitted to appear inside an `optional` container even though the compiler's block-inheritance/copy machinery for those statements does not interact safely with how an optional's contents get independently resolved and, if disabled, torn down; that lets the bookkeeping used to size the type-attribute bitmap drift out of sync with the number of bits actually touched once the neverallow check runs during binary creation, producing a read past the edge of the allocation. The crash is reached purely by parsing and compiling a syntactically valid (if unusual/fuzzer-mutated) CIL policy text; no filesystem, network, or environment interaction is involved.
