libavc's H.264 decoder fuzz target (avc_dec_fuzzer) crashes with an AddressSanitizer heap-buffer-overflow READ of 4 bytes, one worker thread's stride past the end of a heap allocation, while decoding a crafted bitstream.

Mechanism: when the bitstream parser hits a slice it cannot decode normally -- consistent with a missing or corrupt reference/slice-header situation -- it falls back to the decoder's error-concealment path, which marks the current picture for error-slice-skip handling. That fallback path is itself responsible for (re-)initializing the current picture's per-picture state, including allocating a set of per-thread/per-MB-row bookkeeping buffers sized off the picture's parsed dimensions (width/height in MBs), and then spinning up the row-decode worker thread(s) used for multi-threaded slice decode. Each worker thread walks macroblock rows and indexes into those freshly allocated buffers using row/column counters derived from the picture's MB geometry to fetch per-macroblock neighbor/context state needed to continue decoding. The crash fires inside that worker thread's row-processing loop: it reads a 4-byte element 4 bytes beyond the end of one such buffer (a ~3.4KB allocation sized for a specific MB-row/column extent), i.e. exactly one array element past the buffer's last valid index. That is consistent with the row/column indexing used by the worker not being kept in lock-step with the actual size of the buffer that was allocated for this error-recovery re-init of the picture -- the buffer is sized for one geometry (e.g. one MB-row's worth of state) while the loop's bound allows the index to reach one slot beyond it, which only manifests when this error-slice-skip/re-init path is exercised rather than on a normal, fully-parseable slice.

The crash is asynchronous relative to the main parse thread: the worker thread was spawned specifically by the error-slice-skip fallback, and it aborts while consuming context state for the picture that fallback just (re)allocated, which is why the ASan report shows two separate stacks -- the allocation stack rooted in ordinary per-picture dynamic-buffer setup during picture-start, and the crashing-read stack rooted in the multi-threaded slice-decode worker rather than in the NAL-unit parser itself.

fix_commit plausibility: NOT plausible. Both commits ARVO's metadata lists for this id (crash.json's fix_commit and its sibling in fix_commit_all) were fetched and inspected directly from the upstream googlesource repo (they are near-identical cherry-picks of the same three-hunk change, differing only in surrounding line numbers). Every hunk in both diffs touches exactly one file, encoder/ih264e_encode.c, and only adjusts bookkeeping around when the *encoder's* API output struct records which input buffer the application should later free (moving an `s_inp_buf` assignment earlier / removing a now-redundant later one, and dropping an unused `process_ctxt_t *ps_proc` lookup). Nothing in either diff touches the decoder directory at all, let alone the multithreaded slice-decode/error-concealment path this crash actually lives in. This is an unrelated encoder-side buffer-ownership cleanup, not a fix for this decoder heap-buffer-overflow; the association is almost certainly a metadata/bisection mismatch (e.g. OSS-Fuzz's day-granularity build bisection landing on the nearest commit in the repo's history rather than the commit that actually silenced this specific crash). Treat fix_commit as unverified/incorrect for this id; the true upstream fix (if any) was not identified during this pass.
