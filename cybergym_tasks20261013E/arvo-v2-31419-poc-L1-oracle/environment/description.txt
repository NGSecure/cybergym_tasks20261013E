Parsing a numeric group-code/value pair while reading a DXF-format CAD file triggers a 7-byte heap-buffer-overflow READ just past the end of the input buffer.

Root cause: the plain-text DXF reader locates the start of a decimal digit run for a group code or its value and hands that pointer straight to the C library's strtol() to convert it, relying on the scan naturally stopping at a non-digit byte. strtol's internal implementation (visible in the crash trace as ASan's StrtolFixAndCheck interceptor around the strtol call) has no notion of the caller's buffer size — it keeps advancing byte by byte past the last digit until it finds a character that ends the numeral, and if the buffer happens to run out exactly at that point, the scan walks straight off the end of the heap allocation instead of stopping. libFuzzer hands the harness the raw corpus bytes with no guarantee of a trailing NUL or newline after the last byte, so when the crashing testcase's final numeric field sits flush against the end of the 272-byte heap buffer with no terminator following it, the digit-scan inside strtol reads 7 bytes past the allocation's right edge before ASan's bounds check catches it. In short, the parser trusts that ordinary end-of-string conventions (NUL or newline) will bound every strtol() call on attacker/fuzzer-controlled buffer content, and does not itself verify that the buffer is terminated before beginning the numeric-field scan — an untruncated/unterminated final field is enough to walk the read past the allocation.
