libiec61850 (an IEC 61850 substation-automation communication stack) MMS data-value decoder (fuzz_mms_decode target, ASan build): the decoder reads an ASN.1 BER tag byte off the input buffer and then dispatches to one of a large set of per-data-type handlers based on that tag, each handler responsible for interpreting the just-decoded content-length field according to that data type's own encoding rules. The handler for the "bit string" data type unconditionally reads the very first content byte as a "number of unused padding bits" count (used to compute the resulting bit-string's length) before doing anything else with the content -- it never checks that the content actually contains at least that one byte. The generic length-decoding step that runs immediately before dispatch is perfectly willing to hand back a definite-form content length of zero (a legally well-formed, if degenerate, BER encoding), and when it does, the read/write cursor is left sitting exactly at the boundary of the bytes already consumed from the input. Because the bit-string handler doesn't re-check the length before dereferencing its first "content" byte, a zero-length bit-string element causes it to read one byte past the end of whatever buffer was supplied, independent of any other data-type handler in the same dispatch table. Fix: right after the shared length-decoding step succeeds, a new check rejects the element outright (independent of which data type it turns out to be) whenever the decoded content length is zero and the tag is not the one reserved for a length-less terminator marker -- so a zero-length bit-string element is now refused before any type-specific handler gets a chance to assume a content byte is present.
