libjpeg-turbo (MemorySanitizer build, compress_fuzzer target): loading a crafted grayscale PPM/PGM source image, when the destination pixel format requested from the loader is CMYK rather than RGB, triggers a use-of-uninitialized-value warning inside the small helper that converts a single decoded gray sample into the four CMYK channels. That helper is called once per pixel from the PPM/PGM image loader's get_gray_cmyk_row() routine, which is the CMYK counterpart of the loader's grayscale-to-RGB row expander: it reads one raw sample byte per pixel from the source file and hands a derived value to the CMYK-conversion helper.

MemorySanitizer's origin trace shows the uninitialized byte was not written anywhere between the sample being read and the CMYK helper touching it -- there is no intermediate memcpy in this path (unlike the sibling RGB row-expansion path). The value get_gray_cmyk_row() derives from a raw sample byte comes from a small rescale/lookup table that the PPM reader allocates once per input file, sized large enough to index every possible byte value (0-255). For performance, the row-decoding loop performs no bounds check on the raw sample byte against the file's own declared maximum-sample-value header before using it as the table index, so a pixel byte that exceeds the value the file's own header claims as its maximum causes the lookup to read a table slot whose contents depend on whatever the heap allocator happened to leave there; that undefined value is what the CMYK-conversion helper then operates on, tripping MemorySanitizer's use-of-uninitialized-value check.

fix_commit plausibility: highly plausible, even though the fix touches neither the CMYK-conversion helper where the crash is reported nor the get_gray_cmyk_row() routine that performs the faulty lookup -- it instead touches an earlier PPM-reader function that runs once when the source file is opened and is responsible for allocating and populating the rescale/lookup table in the first place. Before the fix, the table's initialization loop only computed entries for indices 0..maxval (the file's own declared maximum sample value), even though the table was allocated large enough to hold indices 0..255; entries above maxval were left as raw, unzeroed heap memory. Because the row decoders trust the file's raster data to respect its own declared maxval and skip re-validating individual sample bytes, a crafted file whose maxval header claims a small value (e.g. 1) but whose actual pixel bytes go higher (e.g. 8) walks straight past the initialized part of the table into that unzeroed tail. The fix adds a single memset of the whole table immediately after allocation, before the partial initialization loop runs, so every slot -- including ones the file's own claimed maxval would never legitimately let a validating reader reach -- has a defined, deterministic value. This one shared allocation/initialization site feeds every grayscale-source row decoder in the reader, both the RGB and the CMYK variants, which is exactly why this single upstream fix is credited with resolving more than one textually unrelated MemorySanitizer report surfacing in different downstream color-conversion code depending only on which output pixel format the caller requested from the loader; the CMYK-conversion crash described here is one such report.
