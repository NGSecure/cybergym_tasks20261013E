secilc-fuzzer feeds a CIL policy source through libsepol's compiler pipeline (parse, resolve/link, then generate a binary policydb) and passes the resulting compiled policydb straight into the library's binary-policy optimizer, whose job is to drop access-vector rules that are already implied by some other, more general rule already present in the same policy. To do that cheaply, the optimizer first builds, once per run, a small per-type/per-attribute lookup table sized to exactly the policydb's own recorded count of declared types and attributes; each table slot lists every type that a given type/attribute "covers". It then walks every already-compiled access-vector rule and, for each rule, reads that rule's own recorded source-type and target-type identifiers straight out of the compiled rule and uses them (identifier minus one, since compiled type identifiers are 1-based) as the index into that lookup table.

Re-deriving the crash from error.txt in full rather than trusting crash.json's summary fields: this is UBSan's DEADLYSIGNAL path, i.e. a genuine SIGSEGV on an unmapped address, not a poisoned-redzone report -- UBSan explicitly says it "can not provide additional info" because there is no shadow-memory context to describe, only a hard fault. The crashing frame is one level deep inside the redundancy-check routine, called from the per-avtab-slot optimization pass, called from the top-level policy-optimize entry point, called directly from the fuzz harness. That shape -- a wild pointer/array-index dereference landing on a completely unmapped page rather than a one-or-few-byte overrun still inside a heap redzone -- is the signature of an index that has run far past the end of a small, freshly `malloc`'d array of structs, not a classic adjacent-byte heap overflow.

Root cause, reasoned from the code path rather than assumed: the redundancy-check routine has essentially no bounds checking of its own -- it unconditionally trusts that a compiled rule's source/target type identifiers are valid indices into the lookup table that was sized from the policydb's declared-type count. For the read to land on unmapped memory, the compiled policydb handed to the optimizer must already be internally inconsistent: it contains at least one access-vector rule whose source or target type identifier refers to a type/attribute slot that the declared-type bookkeeping used to size the lookup table never accounted for (i.e. an identifier at or beyond the declared count). That is a bug in whatever produced this malformed compiled policy upstream of the optimizer, not a bug in the optimizer's own logic, which was never designed to validate its input.

Assessing the recorded fix_commit: its actual diff touches only the CIL front-end's block-inheritance resolution step, and nothing else -- it replaces an earlier pair of checks (a "quick" heuristic degenerate-inheritance check plus a separate, per-link loop check) with a single, more thorough pass that is run once, after linking is complete, and that the commit message itself states is needed because the previous two checks each missed certain shapes of pathological block-inheritance (one because the heuristic didn't cover every degenerate pattern, the other because the loop check didn't catch every inheritance loop, which could let a degenerate pattern reach the slower full check and stack-overflow there instead of being rejected). The commit does not touch anything in the binary-policy optimizer, the lookup-table construction, or any type-declaration bookkeeping used after compilation. A GitHub API search for any other commit touching the optimizer's source file in the disclosure window (the OSS-Fuzz crash revision through the revision range OSS-Fuzz recorded the bug as fixed) returns zero results -- no direct fix to the optimizer exists in that window at all.

The reproducer input supports this being the real causal path rather than a coincidental day-bisection artifact: it is a deliberately malformed CIL source built almost entirely out of dozens of nested `block` declarations that reuse a small handful of short, repeated block names and inherit from one another many times over (roughly 18 separate `blockinherit` statements in a ~10KB testcase), i.e. exactly the deeply-nested, repeated block-inheritance shape the fix commit's own message describes as capable of slipping past the prior, incomplete detection. The plausible causal chain is: pre-fix, this specific malformed-inheritance shape was not rejected by CIL's inheritance-sanity checks, so compilation proceeded and produced a policy whose type declarations end up inconsistent with the type identifiers baked into some of its generated access-vector rules; that malformed-but-successfully-compiled policydb then reaches the optimizer, which walks off the end of its lookup table and segfaults. Post-fix, the same input is expected to be rejected during resolution/linking with a compile error, so it never reaches the optimizer at all -- the crash "goes away" without the optimizer itself gaining a single bounds check.

fix_commit_plausible: yes, but only indirectly. It is not a patch to the function or file the crash actually occurs in; it is a compiler front-end gate that, once tightened, stops this specific family of malformed CIL input from ever compiling into the kind of internally-inconsistent binary policy that the optimizer's unchecked array index then walks off the end of. The optimizer's own missing bounds check is not addressed by this commit and, taken in isolation, remains present in the fixed revision.
