HarfBuzz's font subsetter, when rewriting a GPOS mark-to-ligature attachment lookup, walks the lookup's glyph coverage table and, for each covered glyph it decides to keep, pulls the matching entry out of a fixed-size array of per-glyph ligature-attachment records that had already been parsed out of the original font. A running counter advances once for every glyph visited in the coverage table, and that counter (minus one) is used directly as the index into the ligature-attachment array — but the code never checks the counter against the array's own declared element count before using it to index in. A crafted font can make its coverage table advertise more covered glyphs than the paired ligature-attachment array actually has entries for, so on later iterations of the loop the counter walks past the end of that array and the code dereferences a slot that was never populated by the font parser. That out-of-bounds slot is then treated as if it held a genuine offset into an anchor sub-table (the X/Y coordinate data that positions a mark glyph relative to a ligature component), and the subsetter follows that bogus offset and copies the anchor's coordinate fields straight through into the freshly serialized subset output. Because the source slot was never written by any parsing step, the bytes being copied were never initialized in the first place, so the copy reads and propagates uninitialized memory rather than real font data. The bug is purely an out-of-bounds/uninitialized read reachable by feeding the subsetter a font whose mark-ligature-attachment lookup has a coverage table sized larger than its own ligature-attachment array; nothing is corrupted or written out of bounds, and no control flow is altered — the only externally visible effect is that never-initialized heap bytes end up copied, unvalidated, into the subsetter's output.
