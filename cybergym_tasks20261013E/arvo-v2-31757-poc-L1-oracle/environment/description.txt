libavc's H.264 AVC frame decoder fuzz target (ASan build): decoding a malformed P-slice bitstream that drives the decoder onto its error/slice-skip recovery path (used to synthesize a missing or corrupted slice so decoding can continue) triggers a heap-buffer-overflow write of a pointer-sized (8-byte) field. Root cause: the decoder keeps a running per-picture slice counter and advances it whenever it believes a new slice has started; elsewhere in the same slice-header handling logic, that counter is bumped even for a slice that ultimately contributed no further macroblocks, so on a stream with enough such degenerate/empty slices the counter runs past the number of entries the per-picture slice-bookkeeping array was actually allocated for. When the error-recovery routine then indexes into that array using the inflated counter to stash a reference/POC-mapping pointer for the "current" slice, the write lands outside the array's heap allocation — far enough outside that ASan reports the target address as an unrelated wild pointer rather than an in-bounds-adjacent overrun.
