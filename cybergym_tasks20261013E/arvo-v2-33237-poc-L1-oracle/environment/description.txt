wasm3 WebAssembly interpreter, fuzzed via libFuzzer with a harness that hands raw module bytes straight to the module loader (AddressSanitizer build). After a module is parsed, the loader walks its data segments to copy each one's initial bytes into the module's linear memory. Each segment carries a small constant-expression "offset" that is evaluated (as a signed 32-bit value) to decide where in linear memory the copy should start; nothing in that evaluation step requires the result to be non-negative.

Before performing the actual byte copy, the loader tries to reject anything that would run past the end of the destination buffer: it adds the segment's declared byte length to the offset and compares the sum against the buffer's allocated size. The trouble is in how that arithmetic is done -- the (possibly negative) signed offset is widened into an unsigned, pointer-sized total before the addition. A negative offset whose magnitude happens to match the segment's declared length makes this widened addition wrap back around to (essentially) zero, which trivially satisfies the "does it fit in the destination" comparison no matter how large the destination actually is. The bounds check is defeated without any error being raised.

The copy then proceeds. With the offset negative, the destination pointer has effectively walked backward from the start of linear memory, and the amount of data to be copied is taken at face value from the segment's declared length -- a value that was only ever checked against the (already-bypassed) destination bound, never against how many bytes of segment content the module's own byte stream still has left at that point. Reading that many bytes therefore runs straight off the end of the module bytes supplied by the fuzzer, and AddressSanitizer flags the resulting heap-buffer-overflow as an out-of-bounds read on the source side of the copy.
