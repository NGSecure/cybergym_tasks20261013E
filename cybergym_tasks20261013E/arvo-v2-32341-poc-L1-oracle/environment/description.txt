PHP's bundled oniguruma regex engine, reached through the mbstring extension's case-sensitive POSIX-style multi-byte regex matching entry point (php-fuzz-mbstring target, AddressSanitizer i386 build): the process dies with SIGSEGV on a wild, unmapped read address deep inside the core backtracking matcher, at the exact point where it evaluates an end-of-string anchor opcode -- specifically the "match position is at, or immediately before a single trailing newline that precedes, the end of the subject buffer" check used to satisfy a $-style end anchor. That check calls a small per-character "is this byte a newline" encoding helper, and the helper does perform an explicit bounds guard (current position must be less than the end-of-buffer pointer) before it dereferences the position pointer -- yet the guard evidently still passes right before the dereference lands on unmapped memory. That combination means the bug is not a simple off-by-one at this call site: either the current-position pointer or the end-of-buffer pointer being compared has already been driven far outside the actual subject-string allocation by an earlier step of the backtracking walk, so the "less-than" bounds comparison ends up comparing two pointers that no longer both refer to the same live object and therefore gives a meaningless answer. Because this is a crash-only AddressSanitizer build (no uninitialized-value provenance tracking), the exact earlier mis-advance of the position pointer cannot be pinned further from the crash report alone, but the fault is unambiguously located in the matcher's anchor-evaluation logic that walks the subject string during matching, not in pattern compilation, and it has no connection to PHP's session-handling subsystem.
