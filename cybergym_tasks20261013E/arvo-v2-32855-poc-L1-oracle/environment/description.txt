libvips's GIF image loader (built on the vendored NetSurf GIF-decoding library), reached through the pngsave_buffer_fuzzer's generic buffer-loading entry point when it sniffs a crafted input as a GIF, crashes with an AddressSanitizer heap-buffer-overflow WRITE of 16384 bytes on a background worker thread. The overflow does not happen while the file's header is first being read and "is this a valid GIF" is being decided; it happens later, deep inside libvips's ordinary tile/region rendering pipeline (region-generate -> tile-cache -> sequential-read machinery), while a worker thread is actually producing decoded pixel data for a tile of the image -- i.e. after the loader has already told the rest of libvips that the file opened successfully.

Mechanism: during the loader's initial header-parsing pass, the GIF decoder allocates its per-image decoding state with a small allocation -- in the crash's own allocation trace only 4 bytes are calloc'd for the block that later gets overrun. That size is fixed at that early point in decoding, before the decoder has fully committed to (or cross-validated) the actual pixel geometry of every frame described later in the file. When a worker thread subsequently asks the decoder to produce real frame pixel data, the frame-decoding step bulk-clears/initializes its destination area using a size computed from the frame's own declared image/local-descriptor dimensions -- here, 16 KB -- rather than re-deriving or re-checking that size against whatever was actually allocated for the corresponding structure back when the header was first parsed. A crafted GIF whose local frame descriptor claims dimensions inconsistent with (larger than) whatever the initial, minimal allocation assumed lets that bulk-clear walk straight past the end of the tiny earlier allocation into unrelated heap memory, corrupting it. In short: a buffer sized once, early, off incomplete/placeholder state is later cleared using a size derived from separate, attacker-controlled per-frame geometry, with nothing in between reconciling the two. This is a genuine defect in the library's own GIF decoder, reached through the standard public buffer-loading API and libvips's normal lazy, on-demand region-rendering pipeline that every real caller goes through -- not an artifact of the fuzz harness.

fix_commit plausibility: not plausible for this crash. The recorded fix commit does not touch anything on this crash's call path (region-generate -> tile-cache -> GIF frame-generate -> the GIF frame decoder, all under libvips's GIF/NetSurf-decoder source). Instead, essentially the entire diff is confined to libvips's separate JPEG XL (JXL) image loader -- a different image-format decoder with its own independent source file, sharing no code with the GIF path. Most of that diff is pure build-hygiene noise (renaming a local variable from a reserved-word-adjacent identifier throughout several unrelated functions in that same JXL loader) plus adding a previously-missing "drive the JXL decoder to completion" loop to the JXL load routine; none of it references the GIF decoder, its buffer sizing, or its allocation logic in any way. This id's own upstream OSS-Fuzz issue thread (recorded in this id's meta.json) explicitly names a different commit as the actual fix for this exact crash, confirming the recorded fix_commit is a genuine mismatch rather than an alternate/legitimate co-fix landing in the same commit. Verdict: fix_commit is wrong for this crash -- most plausibly an OSS-Fuzz day-granularity build-snapshot bisection artifact, where an unrelated JXL-loader commit happened to land in the same nightly build snapshot as whatever actually hardened the GIF frame-decoder's buffer sizing.
