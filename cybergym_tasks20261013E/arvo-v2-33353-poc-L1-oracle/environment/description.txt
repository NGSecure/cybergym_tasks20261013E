A malformed JPEG bitstream embedded inside a DICOM (DCM) container triggers a 1-byte heap out-of-bounds READ in libjpeg-turbo's fast baseline-Huffman MCU decoding path (jdhuff.c), reached through GraphicsMagick's DCM coder, which hands the embedded JPEG to the JPEG coder and calls jpeg_start_decompress.

Root cause: the crafted JPEG carries a corrupt Huffman table, so the fast-path Huffman-value lookup in libjpeg-turbo (the HUFF_DECODE_FAST macro in jdhuff.h) computes an out-of-range index into the fixed 256-entry huffval[] table. The index is formed as the decoded symbol plus the table's per-length value offset (s + valoffset[nb]) with no clamping, so a malicious table drives it outside the valid [0,255] range — here it underflows negative, producing the observed read 82 bytes to the left of a 1795-byte heap region allocated by the JPEG marker reader (alloc_small in jinit_marker_reader). It is a far-from-bounds, read-only out-of-bounds array access (a single indexed table read, not a frame-parameter-driven pointer walk-off); nothing is written. Upstream libjpeg-turbo fixed it by masking the index with & 0xFF.
