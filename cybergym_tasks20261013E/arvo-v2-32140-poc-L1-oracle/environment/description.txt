c-blosc2's decompress-frame fuzz target aborts while retrieving a single item out of a malformed chunk: AddressSanitizer flags a bulk-fill (memset-style) call that is handed an out-of-range size -- effectively negative once interpreted as a signed value -- before any codec-specific decompression even starts. Root cause: that fill size is derived from the interaction of two per-chunk header fields, the declared total uncompressed size and the per-block size, which the header parser only cross-checks against each other (one must not exceed the other) without ever bounding either one in absolute terms. A crafted combination of the two makes the arithmetic used to size the chunk's final, partial ("leftover") block produce a value so large it wraps outside the valid range of the signed size type used internally; the runtime's own argument-sanity check on the fill call catches the corrupted size before any actual out-of-bounds memory write happens. The fix rejects any per-block size above a fixed, sane upper bound as soon as the header is parsed, which keeps this downstream arithmetic from ever reaching a magnitude that can misbehave.
