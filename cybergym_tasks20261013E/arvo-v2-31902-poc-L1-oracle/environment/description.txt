A heap-buffer-overflow READ fires while gpac parses a bootstrap-info box inside an ISO-base-media-format file, at the point where the parser hands one of several embedded strings off to a generic string-duplication helper. The box reader repeatedly fills a fixed scratch buffer one byte at a time straight from the bitstream, walking forward until either it copies a NUL byte (treated as the string terminator) or the number of bytes the box header declared as remaining for this field is exhausted. After the loop, if at least one byte was copied, the code unconditionally treats the scratch buffer as a valid NUL-terminated C string and duplicates it into a freshly allocated field on the parsed structure. Root cause: the loop exit condition does not distinguish "stopped because a terminator byte was found" from "stopped because the declared field length ran out first" -- a crafted file can size this field so every byte up to the declared boundary is non-zero, so the loop drains the whole allotted length without ever writing a terminator into the scratch buffer, yet the following code still proceeds to duplicate it as a string. The duplication routine then keeps scanning byte-by-byte past the end of the scratch buffer's heap allocation looking for the terminator that was never written, walking one byte beyond the buffer's bounds before the sanitizer catches the out-of-bounds read. This is an over-read caused by a missing "did we actually find the terminator" check, not by any buffer being sized too small for its declared contents; the same unchecked pattern repeats across every string field this box reader parses (an identifier field, a list of server-entry strings, a list of quality-entry strings, and two further data fields), any one of which can trigger the identical overflow.
