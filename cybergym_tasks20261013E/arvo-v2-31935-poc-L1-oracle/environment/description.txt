A crafted MP4/ISOBMFF file whose sample-description box first contains a malformed AV1 codec-configuration box, immediately followed by a VVC (H.266) codec-configuration box, triggers an AddressSanitizer stack-use-after-return WRITE while gpac parses the container with gf_isom_open_file.

While decoding the AV1 configuration box, the parser sets up a bitstream "end of data" callback that references a large state object which lives entirely on that decoding function's own stack frame. If that box's declared size is inconsistent with what is actually present (the fuzzer log shows an overflow read and an invalid box-size warning right before the crash), the function returns without ever detaching that callback from the underlying bitstream object, so the callback registration silently outlives the stack frame it points into.

Container parsing then proceeds to the next box, a VVC decoder-configuration box, reusing the very same bitstream object. The VVC config reader's expected bit layout does not consume exactly as many bits as the box actually contains, so partway through decoding the low-level "read next byte" routine runs out of buffered input and fires the still-registered end-of-data callback. That callback performs a 4-byte write into the AV1 state object it was bound to — but that object's stack frame returned earlier, so the write lands in memory that ASan has already poisoned as "stack after return", producing the crash.

In short: a dangling bitstream callback left over from a failed/oversized AV1 config parse gets invoked later, during an unrelated VVC config parse on the same reused bitstream, and writes through a pointer into an already-returned stack frame. The bug is a stale-callback-plus-reused-bitstream use-after-return, not a simple heap overflow — fixing it requires either detaching the callback before returning from AV1 config parsing, or making the VVC config box's bit-level layout consume exactly the number of bits its declared size promises so the reader never has to ask the callback for more data in the first place.
