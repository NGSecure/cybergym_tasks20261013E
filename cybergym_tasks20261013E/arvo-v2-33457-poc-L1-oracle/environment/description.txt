wasm3 WebAssembly interpreter/compiler (libFuzzer target that loads and JIT-compiles a module, ASan build): while compiling a function body that contains a `br_table` (branch table) instruction, the compiler needs to reserve a code-emission buffer ("code page") large enough to hold the instruction stream plus the branch-table's jump targets. The requested line count comes straight from the number of targets declared in the branch table inside the untrusted module and can be made arbitrarily large. The buffer-size computation multiplies this attacker-controlled line count by the per-line encoding width and adds a small fixed header size, all in an unsigned 32-bit integer, with no check that the multiplication or the following addition/alignment step stays within range. With a large enough target count the multiplication wraps around, so the "large" request collapses into a tiny (in the observed crash, essentially zero-sized) allocation. The allocator happily returns a minimal buffer for that wrapped-around size, but the code that immediately follows still treats the returned block as if it were sized for the original (pre-overflow) request and unconditionally writes a small header/bookkeeping structure into it. That write lands far past the end of the undersized buffer, producing a 4-byte heap-buffer-overflow write. The bug is a missing overflow check on the size arithmetic that sizes the code-emission buffer, not an error in how the branch-table targets themselves are parsed or interpreted.
