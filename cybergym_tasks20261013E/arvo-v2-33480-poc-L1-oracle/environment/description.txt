AV1's decoder maintains, for each decoded frame, a small heap array that tracks per-row synchronization state for the in-loop CDEF (Constrained Directional Enhancement Filter) post-processing stage when that stage runs across multiple worker threads -- one entry per filterable row of the frame, sized according to how many such rows the current frame has. This array is set up while decoding a frame and is normally left in place across frames so it can be reused rather than rebuilt every time.

At the very end of the fuzz run, once the decoder object itself is torn down (the codec's ordinary cleanup path, invoked after all input has been consumed -- not while any frame is actively decoding), a cleanup routine walks that same per-row array to release the synchronization primitives (a mutex and a condition variable) owned by each row entry before freeing the array itself. To know how many rows to walk, this cleanup routine consults a cached bookkeeping counter on the decoder's state that records "how many rows this array was sized for", rather than deriving the count from the array's own current allocation.

The crafted input decodes more than one frame, with a later frame declaring a different frame height than an earlier one. When only the frame's row count changes between frames -- without also tripping any of the handful of other conditions the allocator treats as a reason to fully discard and rebuild this array (things like a change in chroma subsampling, in whether CDEF is enabled at all, in tile configuration, in the number of decoded planes, or in the number of worker threads) -- the array is left exactly as it was: not freed, not reallocated at the new size. Only the cached "rows this array was sized for" counter gets updated to reflect the new, larger row count. The underlying array itself, however, is still the smaller one sized for the earlier frame's height, because the allocator only ever (re)allocates this array from scratch when the array pointer is still null; an existing, merely wrong-sized array is not resized.

So by the time teardown runs, the cached counter says "N rows" (matching the taller, later frame), but the array in memory only actually holds room for the fewer rows of the original, shorter frame. The cleanup loop trusts the cached counter and walks one row index past the true end of the array to release that (nonexistent) row's mutex/condition-variable pointers, and the read that touches the first field of that out-of-bounds row entry lands just past the end of the heap allocation -- an 8-byte out-of-bounds read that AddressSanitizer flags right as the decoder object is being destroyed, well after any frame-level decoding work has finished.

fix_commit plausibility: highly plausible, verified by fetching the actual patch (crash.json's local fix_files/fix_functions were empty, so this was checked directly against aomedia's upstream repository rather than taken from crash.json). The commit touches exactly one file -- the CDEF buffer-management source file that owns both the allocation routine and the teardown/cleanup routine described above -- and does two things: it factors the per-row allocate and per-row release logic each into their own small helper, and, critically, it adds a new condition to the allocator so that a frame-height-only change (row count differs from what's cached, even when none of the other "rebuild everything" conditions apply) now also triggers releasing and re-deriving that per-row array at the new size, instead of silently leaving a stale, wrong-sized array in place with only the bookkeeping counter updated. That is a precise, minimal fix for the exact stale-array/stale-counter mismatch this crash exercises.
