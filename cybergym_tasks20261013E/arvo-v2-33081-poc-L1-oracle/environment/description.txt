The crash occurs while the bytecode compiler is walking the instruction stream of a data segment's constant initializer expression -- the same code path used to compile ordinary function bodies is reused here with no restriction on which opcodes may legally appear in that context. For every opcode read from the (attacker-controlled) module bytes, the compiler looks up per-opcode metadata -- which specialized routine handles the opcode, and, for value-producing operators, what value type the operator leaves on the operand stack -- by indexing directly into one of two small, fixed, opcode-prefix-selected lookup tables using the raw numeric opcode value, with no check that the value actually falls inside either table's bounds. A crafted initializer expression that drives this lookup to an out-of-range opcode value causes the read to run past the end of the table; whatever bytes happen to sit adjacent to it in memory are then treated as if they were legitimate per-opcode metadata, including the "value type" field. That bogus type value gets recorded as the type of a value later pushed onto the compiler's operand-stack/register model. When a following, unrelated instruction needs to spill whatever value currently occupies a hardware register to a stack slot -- a routine step this compiler performs before emitting several kinds of operators -- it reads that value's recorded type and uses it, unchecked, as an index into a tiny fixed-size table of per-type "store to slot" operations. Since the type inherited from the earlier out-of-bounds table read can be an arbitrary byte, the resulting index falls far outside the table's valid handful of entries, and the sanitizer catches the out-of-bounds array access at that point. The fault therefore does not originate at the spill site itself: it is a downstream symptom of an earlier, unchecked opcode-table lookup performed while compiling attacker-controlled bytecode inside a constant-expression context that was never meant to admit arbitrary instructions in the first place.
