gpac's ISO Base Media File Format (MP4) parser processes a box that records per-sample size values for the movie's sample table: the box declares a total sample count and, optionally, a single fixed per-sample size; when no fixed size applies, the parser heap-allocates one array entry per declared sample and loops over the bitstream extracting each sample's individual size, writing each value into the corresponding array slot. One supported size encoding packs two samples' sizes into a single pair of sub-byte fields per loop iteration (with a trailing zero-padding field when the total sample count is odd, so the last iteration only produces one real value), while the general encoding advances the loop by exactly one sample per iteration. After writing a freshly parsed sample size into the array, the same loop body is also supposed to fold that value into running statistics: the largest sample size seen so far, an accumulated total size, and a running processed-sample counter.

Root cause: the statistics-update step does not use the index the value was actually just written at. It instead re-reads the array using the loop's index variable only after that variable has already been advanced to the position where the next iteration will begin -- advanced by two for the packed dual-sample encoding, or by one for the general encoding. For every iteration except the last, this merely means the statistics are computed from a neighboring array slot that has not been written yet this pass (stale/garbage-influenced accounting, not a memory-safety issue on its own). On the very last iteration, however, the already-advanced index lands exactly one element past the end of the array, which was heap-allocated with exactly as many elements as the declared sample count. Re-reading the array at that advanced index therefore reads 4 bytes immediately past the end of the heap allocation. This is an out-of-bounds heap READ triggered by the bookkeeping code, not a write, and it is unrelated to how the individual per-sample size values are themselves extracted from the bitstream (those writes stay within the allocated array).
