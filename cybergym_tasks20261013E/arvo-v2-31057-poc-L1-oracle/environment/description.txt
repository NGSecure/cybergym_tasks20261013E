SELinux CIL compiler (secilc / libsepol CIL frontend), MemorySanitizer build. The crash happens during AST resolution, after parsing, while the compiler is resolving/copying the contents of nested policy-language `block` constructs -- one block containing a `blockinherit` reference, itself nested inside another `optional` container that also contains a `block`+`blockinherit` pair. Optional-block statements in CIL are meant to be resolvable independently, and their whole declaration subtree can be torn down as a unit once the optional turns out to be inactive or once resolution of its contents finishes. At the time of this bug, the resolver's list of statement kinds that must not appear inside an `optional` covered only a couple of cases; ordinary `block` (and by extension the inheritance/copy machinery that `blockinherit` drives for those blocks) was not on that list, so a block could legally sit inside an optional even though resolving block-inheritance creates additional references into the same AST subtree that the optional's own teardown logic does not account for. When the compiler later walks and destroys the optional's subtree, a tree node that was already released via the block-inheritance copy/cleanup path gets visited and torn down a second time. The sanitizer flags this as a read of a value that was produced by an earlier heap deallocation -- i.e. the teardown code is operating on memory that had already been released, not on live data. The crash is reached purely by parsing and compiling a small, syntactically valid CIL policy text; no filesystem, network, or environment interaction is involved.
