c-blosc2 (MSan build, decompress_frame_fuzzer target): while decompressing a chunk that lives inside an in-memory frame, the frame layer first has to resolve which chunk index maps to which byte offset inside that frame. It locates the compressed sub-chunk that stores the per-chunk offset table and, rather than parsing that sub-chunk's bytes directly, hands it off to a generic single-item extraction helper to pull out just the one 8-byte entry it needs. That helper builds a fresh, minimal decompression context for the call and allocates its scratch/working buffers straight off the heap, unzeroed, before decompressing the target block of the offset table into them. The block-copy step that follows trusts the declared block/leftover span rather than how many bytes the underlying codec actually produced for that block, so when the offset table's trailing block does not fully populate the span the copy assumes it did, the copy still walks the full nominal length and carries a tail of never-written scratch bytes straight through into the caller's output buffer. The frame layer then immediately treats that output as a complete 64-bit chunk offset and reads it back -- which is exactly where the sanitizer catches the problem: part of the value making up that "offset" was never actually written by anything, only allocated. Unlike a wild-pointer crash, nothing here looks obviously invalid at this point -- the tainted offset is silently accepted and would only misbehave further downstream if it were later used to locate a chunk's real position, so this bug class is only observable because taint tracking is watching the read itself, not because control flow visibly breaks.
