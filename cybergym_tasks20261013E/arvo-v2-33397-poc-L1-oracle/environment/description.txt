wasm3 (a WebAssembly interpreter), honggfuzz app-fuzzer target, ASan build. The crash is a SEGV wild-address read that happens at *execution* time, inside the bytecode operator that implements a conditional branch's "prologue" check, reached from the function-call dispatch path while interpreting an already-compiled function. The actual defect, however, is introduced earlier, at *compile* time, not in the interpreter loop itself. wasm3 does not JIT; it first translates each WebAssembly function's bytecode into its own internal threaded-code representation, tracking value-stack slot assignments as it goes. When the compiler processes an instruction that unconditionally ends normal control flow within a block (e.g. an unreachable trap, a return, or one arm of a branch/loop), WebAssembly's validation rules say the operand-stack "shape" from that point on is irrelevant (the following code is unreachable), so the compiler flips the current block into a polymorphic-stack state and, as part of doing so, also needs to unwind/reconcile its own bookkeeping of which value-stack slots are in use for that block. That unwind step can itself fail if the slot bookkeeping is already inconsistent -- but at every call site in the branch/loop/return/unreachable compilation paths, its result code was being discarded (called as a bare statement) instead of being checked and propagated up to abort compilation on failure. Separately, when compiling the conditional-branch opcode specifically, the compiler emits the branch condition's tracked stack-slot index as a literal operand baked directly into the generated bytecode, and that emission call was likewise not being checked for failure. Because both of these failure signals were silently swallowed, compilation of a crafted module can carry on past an already-corrupted slot-tracking state and still finish "successfully", producing a compiled function whose branch instruction embeds a stack-slot index that does not correspond to a valid offset within that function's allocated execution stack. At runtime, the operator that executes this branch instruction uses that embedded index to read the corresponding execution-stack slot in order to decide whether to take the branch; with a bogus index the read lands on an unrelated/out-of-bounds address, and that off-stack pointer's target is what ultimately gets dereferenced, producing the wild-address SEGV that AddressSanitizer reports. In short: the crash is a runtime memory-safety symptom of a compile-time bug where an internal stack-consistency error, arising from mishandling a wasm function's polymorphic-stack transitions, was not propagated and instead allowed to silently emit an invalid stack-slot reference into executable bytecode.
