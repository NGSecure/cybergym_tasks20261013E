SerenityOS's LibMarkdown fenced-code-block parser decides whether a line opens or closes a fenced block by extracting the run of leading fence characters at the start of the line as a text span and comparing that span against the three-backtick fence marker, using a generic span-vs-C-string equality routine shared across the codebase. A Markdown line is free to open a fence with more than three backticks (this is valid, common Markdown syntax used so the fenced content itself can safely contain a run of three backticks), so the extracted leading-fence span can legitimately be longer than the three-character marker literal it gets compared against. The equality routine has no independent bound check of its own for the literal side of the comparison: its iteration count comes entirely from the span's own length, and nothing in the loop stops it from continuing to step through the literal's backing storage after it has already consumed every real character the literal contains -- there is no early-exit the moment it reaches that literal's closing null byte. With a leading-fence span of four or more characters, that missing early-exit means at least one comparison iteration reads a byte that lies past the four-byte fence-marker literal altogether. In this particular build that adjacent byte happens to sit inside unrelated read-only global metadata for the code-block parser's own class, which the linker placed directly after the literal in memory -- so the overrun manifests as a one-byte out-of-bounds read from global (not heap or stack) storage. The trigger is specifically a fence-opening or fence-closing line whose count of leading fence characters is four or more, since exactly three characters never exercises the iteration that would run past the literal.
