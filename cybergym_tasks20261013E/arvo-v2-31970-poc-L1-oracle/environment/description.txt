wolfSSL's cryptofuzz-based wolfCrypt fuzz target (ASan build, with the library's fixed-size "fast-math" bignum backend disabled so it exercises the original heap-allocated arbitrary-precision integer implementation instead): a crash occurs while servicing cryptofuzz's generic bignum-calculator fuzz operation configured to run a raw single-bit-test query — given an arbitrary-precision integer decoded from fuzz input and a second, independently fuzzer-controlled numeric operand, the harness asks wolfCrypt's classic bignum code whether a specific bit position of that integer is set. AddressSanitizer reports a SEGV caused by a READ at an address that bears no relationship to the integer's actual backing storage — a wild out-of-bounds access, not a small over-read adjacent to a buffer's end.

Root-cause mechanism: internally, the bit-test routine converts the caller-supplied bit-position operand into a word-array index by dividing it by the number of bits packed into one storage "digit" of the arbitrary-precision representation. Before ever touching the underlying digit array, it is supposed to short-circuit and report "bit not set" whenever that computed index lands at or beyond how many digits the integer currently actually has in use — this single check is the only thing standing between a fuzzer-chosen bit position and an out-of-bounds read of the digit array. In the vulnerable code, that computed word index (and the leftover within-word bit offset alongside it) is represented, and compared against the integer's used-digit count, using the compiler's ordinary signed integer type rather than the library's own unsigned digit type that the rest of the bignum implementation uses for indices of this kind. cryptofuzz's raw bit-test operation is free to choose the bit-position operand from the full range its parameter type allows, with no application-level ceiling tying it to the size of the integer being tested. For bit-position values large enough to push the computed word index toward the edge of what the signed type can represent, the signed arithmetic no longer tracks the same magnitude the unsigned used-digit count is compared against, so the "this index is out of range, don't touch the array" guard fails to fire, and the routine proceeds to index the digit array at that value. Because the guard was defeated rather than merely off-by-one, the resulting index lands far outside the integer's actual allocation rather than just past its end, which is why the sanitizer reports a wild-address read/SEGV instead of a conventional small heap-buffer-overflow.
