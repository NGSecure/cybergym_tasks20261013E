A heap-buffer-overflow READ fires while irssi parses the IRCv3 message-tags prefix of an incoming server line. The tag string is first split on ';' into one segment per tag, and each segment is then split again on '=' to separate the key from the value; the value half of that second split is handed straight to an unescaping helper with no check that the split actually produced a value slot. Root cause: the code assumes every ';'-delimited segment is a non-empty "key=value" pair, so a degenerate empty segment (e.g. two consecutive ';' with nothing between them, or a trailing/leading ';') falls through to the second split unguarded; splitting an empty string on '=' yields a tiny heap array holding only the list terminator, with no second (value) slot ever allocated. The unescaping call then dereferences that nonexistent value slot, reading one pointer-width past the end of the freshly allocated array -- an 8-byte out-of-bounds read on a 64-bit build. The missing check is simply "is this tag segment empty" before doing the key/value split and touching its second element.
