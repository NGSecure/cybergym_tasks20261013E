wasm3 (a WebAssembly interpreter, MSan build): parsing a crafted wasm module whose global section contains an initializer expression with an `if` opcode (optionally followed by `else`) triggers a wild-pointer read and SEGV while the module is still being loaded, before any function body is compiled or any code runs. A global's initializer is only supposed to accept a narrow "constant expression" opcode set (const literals, a reference to an earlier global, and the terminating end), since it executes outside of any function and without the bookkeeping a real function compilation sets up. The gate meant to enforce that restriction checked the wrong signal: it asked whether a particular scratch/one-off interpreter context (allocated only by a separate, later code path that re-evaluates an already-parsed global's initializer on demand) was the one currently active, rather than asking directly whether a function was currently being compiled. Because that scratch context is never active during the initial, first-pass parse of the global section, the gate always came back negative there, so the initializer's opcode stream fell through to the same full control-flow compiler used for ordinary function bodies.

When that unrestricted initializer contains an `if`, the block compiler treats it exactly like real executable code and asks the interpreter's compiled-bytecode page pool for a fresh page to hold the compiled block. Servicing that request walks/reuses the pool's internal page-capacity list under the assumption that a function is presently being compiled and that the associated per-function compilation state has already been set up — state that simply does not exist while compiling a global initializer at module-parse time. Walking that list under this false assumption dereferences a pointer that was never initialized for this code path, producing the near-null wild read (crash address ~0x2988) that MemorySanitizer reports one frame above the code-page bookkeeping routine, inside the page-acquisition helper the block compiler calls when it opens the `if`/`else` branch.

The fix commit (3c5a5e691ba31ed60c4509e834dfdb40e0fa0220, message "Cleanup") replaces the scratch-context-based gate with a direct check of whether a function is currently being compiled, so a global initializer's opcode stream is restricted to the safe constant-expression subset in every code path that compiles one -- not only the separate demand-evaluation path the old gate happened to detect -- and an `if`/`else` (or any other non-constant opcode) inside a global initializer is now rejected before it can reach the function-body block compiler. The same commit deletes the now-unused scratch-context flag machinery. It is a single, non-merge commit touching exactly the two source files implicated in the crash's own call stack (the block/expression compiler and the runtime/environment module that owned the removed flag), so it is a plausible and directly on-point fix for this crash, not an unrelated or fuzzing-harness-only change.
