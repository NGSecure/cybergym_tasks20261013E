md4c Markdown-to-HTML converter (fuzz-mdhtml target, ASan build): while resolving an inline link/image marker pair, the parser reads one byte past the end of the input buffer if the candidate link destination/title text runs all the way to the very end of the document with no trailing newline. The routine that recognizes a `(dest "title")` link-spec scans past the destination and optional title looking for the closing ')', first skipping trailing whitespace on the current physical line with a bounds-checked loop (stopping once `off` reaches that line's own end offset), then checking whether that scan landed at end-of-line so parsing can continue onto the block's next physical line. That end-of-line check only tests whether `off` has reached the current line's end offset, and then unconditionally probes the byte at `off` to confirm a real line break follows -- but when the link-spec text is on the last physical line of the whole input and there is no trailing newline, that line's end offset equals the byte length of the whole allocated input buffer, so `off` can land exactly on that byte-length value, and the newline probe then dereferences one byte beyond the end of the allocation. This is a read-only, forward/past-the-end 1-byte over-read (matches the ASan report: "READ of size 1 ... 0 bytes to the right of 5488-byte region") driven purely by missing end-of-buffer bounds checking, not by any attacker-controlled length field or off-by-N miscalculation elsewhere.

The associated upstream fix commit is directly on point for this crash: its first hunk rewrites exactly this end-of-line test so it also short-circuits whenever the scan offset has already reached the buffer's total byte length, treating hitting end-of-buffer the same as hitting a real line break, without ever dereferencing past the allocation. The remaining hunks bundled into the same upstream commit touch unrelated call paths not present on this crash's stack: permissive URL/email autolink handling, an added opener case for image markers in the bracket-matching chain lookup, an off-by-one in the marker-chain rollback/unwind logic used when backtracking a failed match, tag-matching/end-of-input handling in the HTML raw-block end-tag detector, and whitespace-skipping after a task-list marker -- these are other, independent fixes riding along in the same commit and are not what this particular ASan report reproduces.
