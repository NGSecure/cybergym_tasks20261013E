PHP mbstring's mb_ereg() family hands the caller-supplied pattern to the vendored Oniguruma regex engine, which compiles interval quantifiers (`{n}`, `{n,m}`) into repeat nodes and, at compile time, combines the repeat counts along a branch to estimate how far a match starting at a given position could extend, so the search step can safely advance/skip ahead during scanning. When a crafted pattern applies two interval quantifiers back to back to the same quantifiable unit -- bounding an already-bounded repeat with a second, outer bound, optionally with a lazy modifier in between -- the compiler folds the two counts together multiplicatively instead of independently capping each one. Root cause: each individual repeat count is checked against the engine's own per-quantifier limit, but the product of two chained counts is never range-checked before being stored into, and later added onto, a scan-cursor offset used by the regex-search optimization path. During the range search the inflated distance value gets applied to advance that cursor, pushing it far outside the actual subject buffer. The following step, which walks backward from the cursor to realign it onto a valid multibyte-character boundary before the byte-wise scan resumes, then dereferences memory near that wild address, which is the out-of-bounds/invalid read the sanitizer reports. The corruption is introduced by the unchecked multiplication of nested/chained repeat bounds at compile time, not by the character-boundary-alignment logic itself, which is only where the bad offset finally gets dereferenced.
