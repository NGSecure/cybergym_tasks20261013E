wasm3 WebAssembly interpreter, fuzzed via a harness that feeds raw bytes straight into the module loader, which then locates and compiles a function (AddressSanitizer build). The compiler walks the function body opcode by opcode, tracking wasm's value stack as a parallel array of interpreter "slot" numbers -- one slot per live value -- so that later instructions know exactly where to read and write during execution. AddressSanitizer reports a wild-address SEGV on a write deep inside the small bookkeeping routine that flips a slot's "in use" bit whenever a new value-stack slot gets claimed for the first time.

When the compiler enters a structured control-flow block that both consumes and produces typed values (a block/loop/if signature with parameters), it saves the incoming parameter stack positions before compiling the block body, so that if the same block gets recompiled for a second pass -- most notably an if's else arm, which restarts compilation from the same starting stack state as the then arm -- the saved parameter slots can be looked back up and pushed onto the stack again for that second pass. Looking a stack position back up is done through a small helper that, given a stack index, returns the slot number recorded at that position, or a reserved "no slot recorded here" sentinel value if the index falls outside what the compiler currently considers valid. That out-of-range condition arises whenever the first pass (the then arm) ended in unreachable, stack-polymorphic code -- e.g. after an unconditional trap or branch -- because from that point on the compiler stops accounting for the block's incoming parameters as ordinary live stack entries the way it would in reachable code.

The code that pushes the saved parameters back onto the stack for the second pass takes whatever slot number the lookup returned and, without checking it against the sentinel, compares it to the first "dynamically allocated" slot number to decide whether the slot needs to be marked as newly claimed. The sentinel is defined as the largest possible 16-bit value, so it always compares as "at or past" that threshold and is therefore treated as a legitimate, freshly-claimed slot. That slot number is then handed straight to the allocation-bookkeeping routine, which uses it directly as an index into a fixed-size, per-function array of per-slot "in use" flags. Indexing that array with the sentinel lands tens of thousands of entries past its end, and the write that flips the "in use" bit for that phantom slot is the wild out-of-bounds write AddressSanitizer flags.

A module whose function body contains an if block with both parameters and a result type, where the then arm ends in unreachable/stack-polymorphic code (for example a trap or an unconditional branch) before the corresponding else arm is compiled, drives the compiler through exactly this path: the first pass leaves the parameter's stack position no longer resolvable, the second pass's parameter-restoring lookup returns the sentinel instead of a real slot number, and that sentinel is then used unchecked as an array index a moment later, in a routine nested a couple of calls below the one described above.
