While libheif's file fuzz target decodes a HEIF/HEIC file, it hands the embedded HEVC bitstream to the libde265 decoder, whose multi-threaded SAO (sample-adaptive-offset) in-loop filtering stage performs a stack-buffer-overflow READ of 4 bytes on a worker thread while post-processing a reconstructed CTB. Root cause: in the SAO "band offset" mode, for each reconstructed sample the filter derives a lookup index by right-shifting the sample's raw value by an amount computed from the frame's coded bit depth, and uses that index directly to look up an entry in a small, fixed-size (32-entry) table allocated on the stack, before any range/plausibility check on the computed shift amount is applied. A malformed/inconsistent high-bit-depth bitstream can make the decoder derive a shift amount that is too small for the actual value range of the sample being filtered, so the resulting index falls outside the table's 32 valid slots and the lookup reads past the end of the stack-allocated table; the sanity check that exists elsewhere in the same routine to catch out-of-range shift amounts only runs after this lookup has already executed, so it cannot prevent this particular access. The out-of-bounds value read is only used to decide whether/how much offset to add to the filtered pixel — no out-of-bounds write occurs — but the read itself is what AddressSanitizer flags.
