OpenThread's CLI UART fuzz target (AFL, ASan build) crashes while a Service Registration Protocol (SRP) server sub-command in the CLI prints back a domain-name string that was previously set through the CLI itself (one CLI command sets the SRP server's domain to an attacker-chosen string; a later, argument-less invocation of the same sub-command reads it back out and prints it). The CLI helper that prints this stored string forwards it directly as the printf-style format argument of a vsnprintf-based output routine, with no accompanying variadic arguments and no literal "%s" wrapper around it. When the stored string happens to contain a printf conversion specifier such as "%s", the sanitizer's interceptor for the underlying vsnprintf call parses the format string, encounters that embedded specifier, and fetches a corresponding vararg via va_arg -- but since the caller supplied none, the value handed back is whatever leftover/garbage bit pattern happened to occupy that argument slot (register or stack), not a real pointer. The interceptor then treats that garbage value as a char pointer and calls strlen on it to measure the string for bounds-checking, and AddressSanitizer catches a SEGV on an unmapped/invalid address during that strlen read. So this is a classic uncontrolled-format-string bug (CWE-134): letting an attacker-influenced value reach the format argument of a printf-family call turns any conversion specifier embedded in that value into an unintended wild-pointer read rather than an overflow of the string's own storage -- the crash is a read of a bogus address conjured up by treating attacker data as a format string, not a write and not a buffer that was merely too small.
