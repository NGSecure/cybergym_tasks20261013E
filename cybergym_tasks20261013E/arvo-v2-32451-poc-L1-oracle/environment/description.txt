Wuffs pixel-swizzler fuzz target (ASan build): an out-of-bounds write occurs while converting a 4-bytes-per-pixel, alpha-premultiplied source image row into a 3-bytes-per-pixel destination row (BGR, no alpha channel). The conversion loop sizes its pixel count and advances its destination pointer assuming exactly 3 output bytes per pixel, but its per-pixel body still stores a 4th byte (forcing it to a fixed opaque value) as if the destination were a 4-bytes-per-pixel format. For every pixel except the last, that stray 4th byte just gets clobbered by the very next pixel's first byte, so it goes unnoticed; but on the final pixel of the row, the stray write lands one byte past the end of the destination slice, which is sized for exactly (pixel count * 3) bytes. Because the destination buffer can end right at the edge of a mapped region, that single extra byte write can fault as a wild-address SEGV rather than a narrow heap-buffer-overflow redzone hit -- the bug is a fixed one-byte-per-call write overrun past the destination slice's true capacity, not anything related to how the source pixels themselves are parsed or validated.
