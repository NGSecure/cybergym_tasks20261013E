FreeImage (ASan build, load_from_memory_fuzzer target): the harness hands an attacker-controlled in-memory buffer straight to FreeImage's file-type sniffer. For content that resembles a RAW camera file, the sniffer's validation path calls into FreeImage's bundled LibRaw sub-library to open/inspect the buffer before any real decoder is ever chosen. LibRaw is not reading from a real file descriptor here -- its buffered-read requests go through a small adapter that turns each request into a callback against FreeImage's own memory-stream reader, which resolves it into a raw byte-copy straight out of the original in-memory buffer the fuzzer supplied. While LibRaw walks the raw file's embedded EXIF metadata (a GPS/maker-note-style sub-block) and asks the adapter for the next primitive value, the byte offset and length it passes down are derived from fields inside the untrusted file content itself and are never checked against how many bytes of the buffer actually remain unconsumed. With a crafted metadata header the adapter ends up copying from an offset that lands nowhere near the real buffer -- the process takes SIGSEGV on a wild, far-out-of-range read address while still inside the EXIF-parsing part of the RAW-validation call chain (sniffer -> RAW-plugin probe -> LibRaw open/identify -> TIFF parse -> EXIF/GPS field parse). Root cause: the memory-stream read callback trusts the offset/length LibRaw derives from the raw file's own metadata fields rather than clamping them to the input buffer's real remaining size, so a single malformed EXIF field is enough to walk the read arbitrarily far past the end of the buffer.
