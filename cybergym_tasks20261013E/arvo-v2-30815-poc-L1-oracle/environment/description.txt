One-line: In PHP's Zend engine, a heap-buffer-overflow READ of 8 bytes happens during per-request teardown, right after an object destructor invoked at that point causes a variable-lookup hash table to be freshly (re)built partway through cleanup.

Crash mechanism (derived from error.txt, not from crash.json's labels):
- The ASan report fires on a READ of size 8 whose target address sits 8 bytes to the *left* of (i.e. just before the start of) a freshly allocated 56-byte heap region — a classic "read one slot before the allocation" / stale-boundary access, not a plain out-of-bounds-forward overrun.
- The allocation trace shows that 56-byte region was created moments earlier by the hash-table constructor, invoked while the engine was lazily materializing a symbol table (the table used to look variables up by name) on first access — some compiled variable had not been bound to a fixed slot at compile time, so accessing it forced this table into existence. That materialization happened deep inside a call chain that starts from an object's ref-count dropping to zero and its destructor method running — i.e. the destructor executed PHP code that accessed a variable dynamically by name (e.g. via a construct like `compact()`/`extract()`/`$$var`) in a scope whose name-lookup table hadn't been needed/built before.
- Critically, this destructor invocation and its side effect (freshly allocating that symbol table) happen *during the engine's own request-teardown sequence* (the shutdown path that runs after the main script has already finished, while the engine is tearing down leftover execution state) — not during normal script execution. The read-crash then happens back in that same teardown routine, immediately after the nested destructor call chain returns.
- Putting the two frames together: the teardown code appears to have cached some notion of a table's identity/bounds *before* running pending object destructors as part of its own cleanup work. One of those destructors, running late, causes that table to be freshly (re)allocated as a side effect of executing ordinary PHP code. The teardown code then resumes with its pre-destructor assumption and dereferences a location relative to the table's *new*, just-returned pointer that lies just outside/before its actual bounds — reading 8 bytes that belong to heap bookkeeping/redzone rather than to any live object. This is an ordering/staleness bug: a table (re)creation triggered as a side effect of a destructor callback that runs later, in the teardown sequence, than the surrounding cleanup code appears to expect.
- This is a real object-lifetime/shutdown-ordering bug in the engine's own bookkeeping, not a fuzzer-harness artifact — the same teardown call chain (deactivate → request-shutdown) is the normal per-request path any PHP request goes through, and a destructor dynamically accessing a variable by name is legal PHP code, just placed at an unusual point (during teardown-time object destruction) that the surrounding cleanup logic didn't anticipate.
