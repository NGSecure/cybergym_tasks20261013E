wasm3 WebAssembly interpreter, fuzzed via AFL with a driver that feeds a raw module directly to the module parser (AddressSanitizer build). While parsing the module's function-signature (type) section, the parser reads, for each declared signature, a count of parameter slots and a count of return slots -- both taken directly, and independently, from the fuzzer-controlled module bytes as 32-bit values. It then allocates a single structure sized to hold exactly (parameters + returns) type-tag bytes, before going on to fill in that array one slot at a time.

There is a sanity check meant to reject a signature that declares an unreasonably large combined slot count, but it is computed by directly adding the two raw 32-bit counts together with no wider intermediate type. A return-slot count chosen near the top of the 32-bit range, combined with a small parameter count, makes that addition wrap around past the top of the 32-bit range and land back on a tiny value -- comfortably under the "too many slots" threshold -- even though the return-slot count itself is still enormous. The oversized-signature check is satisfied, and the allocation immediately afterward is sized off that same wrapped, tiny total, producing a minuscule type-tag buffer.

Parsing then fills the return-slot portion of that buffer by looping once per return slot, writing one type-tag byte per iteration -- but this loop is bounded by the original, un-wrapped, huge return-slot count rather than by the buffer's real (tiny) capacity. The very first writes that walk past the end of the undersized allocation are caught by AddressSanitizer as a heap-buffer-overflow write.
