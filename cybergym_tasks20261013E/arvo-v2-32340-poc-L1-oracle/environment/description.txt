A crafted regex pattern that gives the compiled matcher a large minimum-possible-match-length distance value triggers a use-of-uninitialized-value warning (MSan) while the engine positions its scan pointer at the start of a search over an EUC-JP-encoded haystack. Root cause: before stepping the scan pointer forward character-by-character toward the minimum-distance target, the code first checks whether the remaining haystack is even long enough to contain a match of that minimum length, so it can fail out immediately if not -- but that guard compares the remaining length against the minimum-distance value only after implicitly truncating the distance to a narrower signed integer. For a minimum-distance value large enough to overflow that narrower type, the truncated value no longer reflects the true, much larger minimum, so the "too short, fail now" exit is wrongly skipped even though the haystack really is too short for it. Execution then falls into the per-character advance loop, which uses the full, untruncated minimum-distance value as its target and so walks the scan pointer past the end of the meaningfully-populated input bytes into unwritten heap memory. Each step of that loop calls a per-byte encoding-length lookup that indexes a fixed table using whatever byte currently sits under the pointer, and it is that indexed read of a still-uninitialized byte that the sanitizer flags. The defect is in the pre-advance remaining-length guard when the pattern's minimum match distance is large enough to overflow the comparison's narrower integer type; the encoding-length lookup table itself is not at fault.
