The loader parses the module and then, for each global with an initializer and each data segment's offset expression, compiles that small, self-contained expression into a short run of interpreter operations and immediately executes it -- reusing the runtime's already-allocated operand-stack buffer to hold the values the expression pushes, in order to read off the resulting constant. AddressSanitizer reports an 8-byte out-of-bounds write into that buffer while one of these compiled operations is executing a constant-push step.

The compiled expression's instructions were never validated to fit inside the buffer that was about to run them. Ordinarily, whenever the compiler emits an instruction that claims another slot of operand-stack space, it also bumps a running high-water mark of how many slots the code being compiled will need, and a check performed right before that code runs compares the mark against how much stack the runtime actually has available, refusing to proceed if it doesn't fit. That bookkeeping step, however, is only wired up while compilation is happening in the context of a genuine, fully set-up function. Compiling a global's initializer or a data segment's offset expression goes through the very same instruction-by-instruction compiler, but does so outside of any real function context, so every slot claimed while compiling one of these expressions is invisible to the high-water-mark tracking: the mark simply never advances, and the later check has nothing meaningful to compare against.

A module whose data-segment offset expression consists of a long, otherwise well-formed run of constant-push instructions with no early end marker exploits exactly this gap. Nothing during compilation objects to the growing number of slots being claimed, nothing stops the resulting bytecode from being handed off for execution, and the operand-stack buffer -- sized for a call depth the (unrecorded) high-water mark never reported -- simply runs out partway through. The specific write AddressSanitizer flags is one push, near the end of that long chain, landing eight bytes past the buffer's end; the fault is a consequence of the missing bookkeeping earlier in compilation, not of anything unusual about that particular push itself.
